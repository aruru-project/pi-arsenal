# 写有用的测试

测试是用来抓错误的，不是用来制造漂亮数字的。

## 先判断是否值得自动化

不是每次代码修正都需要新增测试。自动测试适合有稳定、客观、可重复判断的结果。

- 文案、视觉、交互感受和设计判断如果没有稳定的自动判据，就修正后真实查看并人工检查，不写禁词表或字符串自证测试。
- `never`、`rejects`、`bounded`、上限和异常输入测试，必须来自真实事故、安全边界或冻结的外部合同；不要为理论风险写测试。
- 不要把当前实现的限制写成产品合同。主人本来应该能做但程序暂时做不到的事，不应由测试永久禁止。
- 如果说不清测试失败时哪个调用方会得到错误结果，就不要写。

## 动手前

先读项目已有的测试说明和附近测试。但附近测试违反本 skill 时，它们是反面教材，不是模板：不要因为"周围都这么写"就模仿存量的自证 Mock、机制断言或巨型测试。配额和风格以本 skill 和项目 QA 文档为准。每准备增加一个测试，先回答：

1. 我刚改了什么？
2. 它最可能让调用方看到什么错误结果？
3. 现有测试能不能抓住？
4. 能不能从问题真实发生的入口复现，而不是只测试修复时新加的 helper？
5. 新测试失败时，能不能直接看出哪项能力坏了？

条件允许时，先在修复前确认测试会失败，或临时恢复那个错误确认它会失败。测试如果只会在内部结构变化时失败，而用户结果仍然正确，就不要写。

## 怎么写

- 修 Bug：优先写一个从原始故障入口复现 Bug 的测试；不是给修复代码本身写测试。
- 写新功能：测试调用方真正依赖的结果，不要照着源码逐步复述。
- 一个测试只需要一个清楚的失败原因；围绕同一结果可以有多个必要断言。
- 测试标题必须说出用户动作和可见结果。标题里出现 projection、generation、cursor、mutation、dedup 这类机制词时，先重想这个测试在保护谁；说不出来就不写。
- 不同输入只有在可能触发不同错误时，才值得分别测试。
- 已有测试能抓住同一个错误，就补强它，不要复制一份。
- 选择最省事但确实能碰到问题的测试方式。便宜的测试证明不了，就换更接近真实使用的方式。
- 用户可见界面优先走真实交互入口。reducer、formatter、layout 测试只能证明局部逻辑，不能证明整体可用或“像人话”。
- Mock 只用于隔开稳定的外部边界；预期结果必须来自需求或独立事实，并断言调用方最终得到的结果。
- 测试用的 fake/fixture 只能录制请求、返回测试内声明的固定应答。它不得 import 被测系统的常量、helper 或算法来生成应答，也不得自己实现被测系统的投影、分页、事件翻译或协议逻辑——那是第二套实现，真实现坏了它照样给出"正确答案"。发现 fake 已经长成第二套实现时，先拆 fake，再写测试。

## 不要这样写

- 不要为了测试数量或覆盖率增加测试。覆盖率只能帮助找遗漏，不能证明功能正确。
- 不要换很多组数据反复检查同一件事，再把循环次数或断言次数当成测试数量。
- 不要新增 mapper、adapter 或 helper，再直接测试它的 switch/映射结果，并声称原问题已经被复现。
- 不要 Mock 出正确答案，再证明程序拿到了这个答案。
- 不要使用被测代码的同一套 helper、常量或计算过程生成预期答案。
- 不要用文字、函数、文件或某行代码“存在”，冒充功能真的能用。
- 不要用禁词正则、完整字符串快照或固定文案清单证明界面自然、清晰或没有内部信息。只有明确冻结的产品文案才测试精确文字。
- 不要只检查内部调用顺序、中间状态或调用次数。只有“外部副作用必须恰好发生一次”本身是产品或安全合同时，调用次数才是结果的一部分。
- 不要用测试专用 flag、对象身份或手工状态，冒充真实结果。
- 不要因为测试失败就直接修改期望值。先确认是实现错了、测试错了，还是需求变了。
- 不要把当前测试没有覆盖的运行方式写成“已经验证”。

循环、参数化测试和 Mock 不是一律禁止。它们必须覆盖不同的真实风险，而不是帮助测试数量膨胀。

## 交付前

- 运行与改动直接相关的测试，并按项目要求执行必要的检查。
- 确认新增测试能因目标错误而失败，不是依赖当前实现才能成立的自证题。
- 对用户可见界面，实际查看最终渲染或真实交互，不拿局部单元测试替代人工判断。
- 若现有测试要求保留错误行为或内部结构，先把它当作测试缺陷审查，不要扭曲实现去满足它；是否删除按任务范围和项目规则处理。
- 删除或合并没有独立作用的重复测试。
- 说明哪些地方仍然没有被证明，不要用猜测补齐。

## 汇报

按这个格式说人话：

```text
测了什么：
- <通过什么入口验证了什么结果>

这些测试能抓住：
- <具体错误>

还没证明：
- <未覆盖的运行方式、风险或需要人工判断的部分>
```

可以汇报执行了哪些命令以及是否通过，但不要把测试数、断言数或覆盖率当作质量证明。

## 反面教材

- ❌ 用和源码相同的计算过程生成预期结果，然后比较两边相等。
- ❌ 新增错误映射函数，再给它喂自造错误并断言映射后的文案。
- ❌ 用禁词表或完整字符串快照证明界面“像人话”。
- ❌ 给同一条正常流程喂一百组相似数据，最后宣称新增了一百个测试。
- ❌ 检查某个函数被调用，就宣称用户最终能得到正确结果。
- ✅ 构造一个真实会出错的场景，从原始入口检查调用方最终看到的结果，并让失败信息直接指出问题。
